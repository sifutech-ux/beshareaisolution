## Implementation and exact file responsibilities

- `webhook/index.php`: preserve the existing GET challenge block exactly;
  403 for missing/malformed/wrong/tampered signatures, 503 for missing secret,
  405 for non-GET/POST, 413 for oversized body, 400 for invalid signed JSON.
  The app secret comes only from the existing private config loader. Verify
  before loading legacy handlers or decoding the body. Intake requires both
  the fixed legacy phone and configured WABA; missing binding returns 503 for
  message events. Lifecycle processing remains signed and retryable.
- `os/src/WhatsAppWebhook.php`: messages/statuses retain WABA in the encrypted
  payload and resolve a connection by WABA **and** phone. Unknown/mismatched
  combinations remain unscoped. Unscoped message/status dedupe keys are separate
  so they cannot consume a known tenant's key. Known tenant dedupe keys remain
  unchanged; no migration or replay of historical events is performed.
- `os/src/LegacyDesk.php`, `whatsapp/meja/guard.php`: reuse `beshare_os` cookie
  and existing login at `/whatsapp/masuk.html`; reread active user membership,
  active business and owner/admin role on every request. Never trust a role
  supplied in a session or request. Require an explicit private business
  binding for the singleton legacy JSON store. Reject client tenant/WABA/phone
  selectors, unknown actions, and missing/invalid CSRF before handlers.
- `whatsapp/meja/index.php`, `perbualan/index.php`, `pesanan/index.php`: guard
  each entrypoint before reading business files or rendering forms. Allow
  bank/token/script edits and pause only. Website fetching/training is paused
  during P0 (its existing redirect/DNS fetcher needs separate SSRF review).
  Resume/reply remain unavailable; UI no longer claims token save enables AI.
- `whatsapp/meja/lib.php`: replace the outbound transport with unconditional
  `false`; no environment flag, token save or action can enable sending.
- `whatsapp/sambungan/webhook.php`: bounded raw input and generic config error.
- `os/src/PrivateConfig.php`, `os/src/Db.php`: always discard include output
  even when private config throws, preventing partial output from leaking.
- `os/tests/p0-fixture.php`, `os/tests/run-security-p0.py`: disposable HTTP/DB
  harness and synthetic fixtures; fixture refuses non-CLI execution.
- `os/bin/check-meta.php`, `check-worker.php`, `check-lifecycle.php`: update
  fixtures for required WABA and signature checks. Worker corruption is tested
  after genuine synthetic delivery/authorization. A foreign-WABA message in a
  lifecycle batch must not enter the legacy tenant's store.

## Configuration contract — prepare only, do not apply to production

The existing `BESHARE_OS_WEBHOOK_CONFIG` points outside the repo/web root to a
PHP array. It already supplies `app_secret`, `verify_token`, `token_key` and
optional `token_key_version`. The new private **string** fields are:

| Field | Meaning |
| --- | --- |
| `legacy_business_id` | Verified OS business numeric ID owning the existing legacy JSON files |
| `legacy_waba_id` | Verified numeric WABA owning fixed legacy phone `1443799975474056` |

Do not guess either value or populate them from a browser request. Explicitly
reconcile the legacy store's data ownership against OS users/businesses and
Meta ownership before a future release. This is a single-tenant compatibility
boundary, not a shared multi-tenant JSON store. Do not repoint its binding to a
new tenant while leaving old data in place. New tenants use OS-scoped storage.
Without the binding, authenticated Desk access is 503 and legacy message intake
is 503; anonymous Desk requests are 401. Login requires existing OS DB config
and active owner/admin membership. No legacy password/session fallback exists.

The GET challenge retains its existing verifier and does not require the new
secret or binding. No verify token or app secret is included in this PR.
No new schema migration is introduced. Existing OS coexistence code depends on
0001–0003; production schema must be inventoried before any later release.

## Validation

Run with PHP CLI (pdo_mysql and mbstring), Python 3 and MariaDB binaries on PATH:

```sh
python3 os/tests/run-security-p0.py --extended
node os/bin/check-signup-event.mjs
```

The harness initializes a brand-new datadir under a mode-0700 temporary folder,
runs MariaDB with `--no-defaults --skip-networking` over a private Unix socket,
and binds PHP HTTP to loopback on an ephemeral port. It clears inherited
`BESHARE_*` configuration, uses only synthetic data/secrets, disables PHP outbound
curl/file HTTP, and stops its processes and deletes its datadir on exit. It
never accepts an external DB endpoint. Extended suites run in a temporary source
copy with their historical fixed lab connections redirected to that socket.
The existing fixed `/tmp/maria-lab.pw` or port 3307 are not touched.

The 370 PHP/DB checks cover signed/unsigned/tampered/malformed requests,

## Next MVP path — outline only

1. Verified incoming message → exact WABA/phone → active tenant, encrypted durable
   event and transactional dedupe. Prove callback delivery and queue behavior
   in a separately approved staging flow before considering production.
2. Tenant-scoped business knowledge with source/version/owner approval; isolate
   retrieval by business ID. Replace legacy shared files and review URL-fetch
   SSRF, redirects, DNS rebinding, upload limits and retention before enabling
   website ingestion.
3. A separate worker calls Gemini with that tenant's approved context, strict
   timeout/budget, no cross-tenant cache, redacted logs, and evaluation fixtures.
   Save a draft response only; outbound stays OFF.
4. Persist human handoff/assignment/pause state. Owner/admin sees the draft,
   customer context and reason for handoff; low confidence, missing knowledge
   and user requests transfer to a human. AI must respect the pause atomically.
5. Only after separate release approval: sender with consent/window rules,
   durable outbox/idempotency, audit trail, rate limits and an operational kill
   switch. Coexistence remains optional for the first MVP.

Remaining legacy limits include bounded file-based dedupe (last 200 IDs), no
atomic transaction across legacy intake files, and historical plaintext JSON
storage. The P0 boundary restricts access but does not migrate or encrypt those
historical files. These must not be presented as production MVP completion.
